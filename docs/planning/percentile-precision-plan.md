# 백분위 정밀값 안정화 후속 PR 제안

> 최신 결정 반영: 추가 정정 분포 승격 후 [원정밀도 검증](../validation/reference-refresh-correction-20261012.md)을 통과했다. 현재 총점 대조 기준은 반올림 없는 정확 동등성이다. 초기 “총점 6자리” 제안은 채택하지 않고 아래를 수정했다. Q6는 raw 비교 키의 후속 제안으로만 유지한다.

2026-10-12. #37은 사용자 결정에 따라 표시 소수 둘째 자리·순위·신뢰도 일치로 복구를 승인했다. 이 문서는 **별도 PR의 제안이며 구현·명세 변경·원격 실행 승인이 아니다.** base main, 제안 브랜치 `s3/percentile-precision`. #37 이후 진행한다.

## 문제와 범위

[원격 검증](../validation/reference-refresh-remote-20261012.md)의 b 총점 차이는 +0.0012711577139441488이다. 직접 원인은 승하차 raw `25550.999999999996`와 `25551`의 IEEE 동등 비교가 서로 다른 백분위 동점 집합을 만든 것이다. 확인된 상류 원인은 임시 CSV 복제가 `extra_float_digits=3`을 누락해 원천 float 비트를 반올림한 것. 이를 합산 순서 차이만으로 설명하지 않는다. 이후 바이너리 복제 23테이블 해시가 일치했고 정확한 원천으로 재생성한 결과도 확보했다.

현재 `lib/scoring/percentile.ts`의 전체 분포 경로와 `score_reference_percentiles` RPC는 `<`/`=`를 그대로 사용한다. CSV 복제 정밀도 보존은 필수이며, 별도로 백분위 비교에 사용할 수치 정밀도를 계약으로 정하는 것이 이번 후속 과제다. 원천 원값·근거·cluster 고정 스케일·가중치는 보존한다.

## 선택지와 추천

| 선택지 | 장점 | 한계 | 판단 |
|---|---|---|---|
| A. 합산된 raw를 고정 자릿수로 반올림한 뒤 백분위 비교 | 분포와 후보 모두 동일한 동점 기준을 쓰며 이번 끝자리 차이를 제거 | 반올림 경계에서 실제 동점 묶음이 바뀌므로 영향 분석·버전 구분 필요 | **추천** |
| B. 집계 입력을 안정적인 키로 정렬해 합산 순서 고정 | 같은 비트의 입력에 대한 연산 순서를 재현 가능 | 이미 반올림된 원천은 복원하지 못하며 중첩 집계·클라이언트 계산 순서까지 관리해야 함 | 단독 해결책으로 비추천, 필요 시 보조 |

**추천 초안: `flow`, `transit.subway_boardings_golden`의 최종 raw를 소수 6자리, decimal half-up으로 반올림한 비교 키(Q6)로 바꾸고, 분포의 각 값과 후보 값에 같은 처리를 적용한다.** 총점이나 후보 입력 한쪽만 반올림해서는 안 된다. 원천 행별 반올림은 하지 않으며 합산 결과의 비교 키만 만든다. 정수 계수 지표는 그대로, demand·거리·saturation 등 다른 raw는 차이를 기록하고 추가 적용 필요 여부를 영향 분석에서 보고한다. cluster 절대 스케일은 대상이 아니다.

이번 전수 분포에서 확인된 최대 raw 차이는 1.1641532182693481e-10으로 Q6보다 작다. 다만 이것만으로 모든 경계값이 같아진다고 보장하지 않는다. 0.5×10^-6 경계 양쪽·정확히 경계·0·NULL·지수 표기·큰 값에 대해 별도로 검증한다. 실제 차이가 계속 남으면 허용오차를 임의 확대하지 않고 원인을 보고한다.

Q6 비교 키는 10^6 배율 정수로 취급하여 float 곱셈 뒤 `Math.round`만 적용하는 방식의 경계 의존성을 피한다. SQL/TypeScript가 같은 decimal 변환·half-up 규칙을 따르도록 구현하고 정수 범위도 검증한다. 라이브러리 추가 없이 가능한지 먼저 검토한다. 원정밀도 raw는 근거/감사에 남기며, RPC가 되돌려주는 원래 요청 raw의 동일성 검사(`reference_raw_mismatch`)와 비교 키를 혼동하지 않는다.

## 앞으로의 로컬·원격 대조 기준 제안

아래 기준은 이번 #37의 표시 정밀도 예외와 분리한다. 사용자 승인 후 후속 PR의 완료 기준으로 고정한다.

| 대상 | 추천 일치 기준 |
|---|---|
| 전제 | 같은 원천 비트·좌표·반경·층·모델·preset·reference snapshot·정밀도 정책. 복제는 COPY BINARY 또는 efd=3 + 바이너리 해시 확인 |
| Q6 적용 raw | 소수 6자리 비교 키 **정확히 동일**, 원raw 차이는 따로 기록 |
| 백분위 동점 | `less/equal/population_size` 정수 **정확히 동일** |
| 백분위·8축 점수·총점 | **반올림·허용오차 없이 Number 정확 동등성**, 원정밀도 차이를 함께 기록. 총점 불일치 시 Ready 불가 |
| 화면 | 현재 표시 규칙의 **소수 2자리까지 동일** |
| 순위·신뢰도·결측·사유 | 순위/동률 집합·신뢰도 정수·NULL·사유 코드 집합 **정확히 동일** |

계산 시각·호출 시간은 점수 동일성 비교에서 제외한다. NULL을 0으로 치환하지 않는다. 이번 차이처럼 두 자리 화면은 같지만 여섯 자리 총점이 다른 경우, 현재 및 후속 정밀값 안정화 PR에서는 실패로 판정한다.

## 구현 계획과 검증

1. `docs/planning/scoring-spec.md`, 운영 reference 계약에 비교 정밀도·half-up·적용 지표·정책 버전을 먼저 명시하는 별도 문서 커밋. 현재 v0.4.0 정의를 이번 #37에서 바꾸지 않는다.
2. `lib/scoring/percentile.ts`와 공용 비교 키 유틸, `ingest/score_reference.py`/검증 스크립트, compact RPC 소비 어댑터 및 SQL 백분위 경로를 동일 규칙으로 맞춘다. 구버전 클라이언트와 원분포 읽기는 보존하고 버전 분리 방식을 구현 계획에서 확정한다. 새 RPC/함수 migration이 필요하면 `supabase migration new`로 생성하고 기존 객체 변경 여부·dry-run을 보고한 뒤 원격 push 승인을 받는다.
3. 원정밀도 분포를 보존하면서 양쪽 비교에 Q6를 적용한다. 옛/새 정책 혼용을 방지하도록 응답/manifest에 정밀도 정책을 식별한다. 원격 데이터 재생성·교체가 필요하면 별도 manifest 승인 대상이다. 이번 로컬 `20261012T013000Z`를 임의 승격하지 않는다.
4. 이번 b raw 두 값, 합산 순서를 바꾼 합성 fixture, half-up 경계 fixture로 SQL·TS·전체 분포·compact RPC의 동점 수를 대조한다. 같은 집계값인 경우와 실질적으로 다른 값인 경우를 구분한다.
5. 정확한 바이너리 원천에서 162,032행의 동점 집합 변화·최대 백분위 변화·변경 건수를 보고한다. a~e와 고정 무작위 5셀의 8축/총점/순위/신뢰도를 전후 비교하고 위 원정밀도 기준을 로컬 및 실제 익명 authenticated 원격 경로에서 검증한다.
6. RPC DB 6조합 각 30회(콜드/웜 분리), production 총점 표시·슬라이더 기존 기준을 검증한다. 쿼리 때 Q6 적용의 인덱스/스캔 비용을 실측하고, 필요 없는 저장 열·인덱스는 미리 추가하지 않는다.

리스크는 동점 집합 변경에 따른 점수 변화, SQL/JS 반올림 경계 차이, 기존 클라이언트와 정책 혼용, 쿼리 비용이다. 코드 롤백은 이전 비교 정책으로 복귀하되 해당 정책의 reference/manifest와 짝을 맞춘다. 기존 9/23·10/11 분포 백업을 유지한다.
