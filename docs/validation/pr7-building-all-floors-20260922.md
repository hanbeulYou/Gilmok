# PR 7 — building.all_floors 추가 검증 (2026-09-22)

입력 계약 v1.2는 기존 v1.1 응답에 `building.all_floors` 배열을 추가한다. 요청 층 `floor_use` 및 나머지 기존 건물 필드는 그대로 유지했다. PR #10, base main, 머지 보류.

10m 남쪽의 도형 없는 보완 좌표 `(127.057585668895,37.5024823498996)`에서도 동일 주소의 기존 유효 캐시를 읽어 전 층 5행이 일치했다. 2026-09-21 실제 BuildingHub 응답을 재사용했으며 외부 API를 새로 호출하거나 현장 방문하지 않았다. 기존 캐시 payload.floors에 전체 층 원문이 있어 worker/캐시 구조 변경이나 강제 만료는 필요 없었다.

[두 경로×두 요청 층 전체 실제 JSON](pr7-building-all-floors-20260922.json). 수정 전 3/4층 응답과 비교해 all_floors를 제외한 building 객체가 정확히 동일함을 확인했다. 요청 층이 없는 경우에도 all_floors는 확보한 전 층 행을 반환하고 floor_use만 NULL이다.

## 계약·호환·검사

- all_floors는 항상 배열이다. 대장/층별 자료가 없거나 후보가 없으면 []; 실제 건물의 층수 0이라는 뜻은 아니다.
- 항목은 floor_no(integer/null), floor_kind(string/null), use_name(string/null), area_m2(number/null). 지하 번호만 음수로 바꾸고 옥탑 등은 원천 층 구분을 함께 반환한다. 같은 층의 복수 용도·중복 행을 합치거나 제거하지 않는다.
- 기존 4인자 호출, 선택 address, 30일 캐시, floor_use 타입/NULL 정책과 요청 층 원문 행 순서를 보존한다. 해당 대장 PK만 조회하고 주변 다른 건물의 층을 섞지 않는다.
- 마이그레이션은 CLI로 생성했다. `20260922044742`는 생성 중 적용된 빈 no-op 이력이라 보존하고 실제 함수 변경은 `20260922045014`에 있다. 기존 적용 마이그레이션·원천 데이터는 변경하지 않았다. 원복은 새 CLI 마이그레이션으로 v1.1의 building/address_building/score_inputs 정의를 복구하면 되며 테이블·캐시 삭제가 필요 없다.
- 단위/회귀: 지하·지상·옥탑, 같은 층 복수 행, 없는 요청 층, 도형/대장/층 자료 없음, 주소 pending/기존 캐시 적중을 검사했다. 주소 캐시 재조회 큐가 생기지 않음도 확인했다.
