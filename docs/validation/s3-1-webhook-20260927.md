# S3-1 머지 후 웹훅 실증 — 2026-09-27

**후속 상태:** 2026-09-29 PAT 권한 수정 후 웹훅 실증은 성공했다. [성공 run·cache ready·RPC 재조회](s3-1-closeout-20260929.md)를 따른다. 아래는 2026-09-27 실패 이력이다.

**당시 S3-1 완료 보류.** 익명 세션의 실제 주소 1건은 pending으로 생성됐지만 GitHub dispatch가 HTTP 403으로 거절됐다. Actions run은 생성되지 않아 run URL이 없으며 캐시 ready·RPC ready 재조회는 미실행이다. 종료 처리에서 Repository variable을 false, DB 트리거를 disabled로 복귀하고 테스트 Auth 사용자를 삭제했다. pending 행은 보존했고 외부 대장 워커는 실행하지 않았다.

## 확인한 기준 상태

## 실제 pending 1건과 실패 지점

공개 학원 주소 원본에서 지오코딩이 확인된 **서울특별시 강남구 역삼로 452**를 사용했다. 좌표 `(37.5022026747964, 127.056660127756)`, 반경 800m, 3층. 이 좌표를 포함하는 적재 건물 도형이 없고 주소 대장 캐시에도 없어 `score_inputs`의 주소 fallback을 사용한다. 캐시를 비우거나 허위 좌표를 만들지 않았다.

GitHub 응답: `Resource not accessible by personal access token`. 응답 헤더 `x-accepted-github-permissions: contents=write`. Vault의 `gilmok_github_dispatch_token`은 `.env`의 값과 일치하므로 다른 토큰이 저장된 문제는 아니다. 값은 출력·기록하지 않았다. [오류·복귀 상태](s3-1-webhook-error-20260927.json).

재개 조건은 해당 fine-grained PAT에 `hanbeulYou/Gilmok` 저장소 **Contents: Read and write** 권한을 부여하거나, 그 권한을 가진 토큰으로 `.env`를 갱신하는 것이다. 새 토큰이면 Vault도 같은 승인 범위에서 갱신해야 한다. 현재 pending 1건을 별도 검토 없이 추가 생성·초기화하거나, CLI의 다른 토큰으로 dispatch를 우회하지 않았다. 실제 webhook→Actions 경로가 통과해야 완료다.

## 웹훅 재확인 — 12:38 UTC

사용자의 재확인 요청에 따라 **기존 pending 1건을 그대로 둔 채** 실패한 웹훅의 고정 repository_dispatch 이벤트를 pg_net으로 재전송했다. Vault 토큰과 이벤트 body/headers는 원래 웹훅과 같고, 새 주소 요청이나 임의 상태 전환은 만들지 않았다. 원래 트리거 호출은 앞선 실증에서 확인했으며 이번 단계는 실패 이벤트의 운영 재전송이다.

- Vault 값은 현재 `.env`와 일치하여 갱신하지 않았다.
- pg_net request id 2 역시 **HTTP 403**, `Resource not accessible by personal access token`, 요구 권한 `contents=write`.
- 전체 20.741초. Actions run 없음, cache ready·RPC ready 미실행.
- variable=false, 트리거 D, 테스트 Auth 사용자 삭제 완료. pending 1건 보존.
- [단계·시간](s3-1-webhook-retry-20260927.json), [응답·복귀 확인](s3-1-webhook-retry-error-20260927.json).

## Vercel 실제 변수 이름·배포 확인 — URL 정정

사용자가 정확한 URL **https://gilmok-weld.vercel.app/**을 알려줬다. 실제 대상은 **hanbeulyous-projects / gilmok**이다. 앞서 조회한 vineyard/gilmok 및 gilmok-hazel.vercel.app은 다른 프로젝트였다. 그 프로젝트의 404·빈 배포 목록을 실제 서비스 상태로 적용하지 않는다. [이전 조회](s3-1-vercel-20260927.json)는 확인 이력으로만 보존한다.

- `/compare` HTTP **200**. Production deployment `dpl_K9zpPtdmMtFFoN8uUgiazWTxXJy2`는 **READY**, main SHA `c0091ae0463e182dad7192403cc28ee2b77003b1`(PR #20)이다.
- 프로젝트 환경변수 API(`decrypt=false`)에서 25개 이름·Production/Preview 적용을 확인했다. Deployment API의 `env`에도 두 공개 변수 이름이 존재한다. 값은 문서·로그에 남기지 않았다.
- **실제 새 브라우저에서는 JSON 대신 “Supabase 연결 설정이 필요합니다.”**가 표시됐다. signup/RPC 요청은 0회. 따라서 HTTP 200·배포 READY와 제품 JSON 검증 통과를 구분한다. [브라우저 결과](s3-1-deployed-browser-20260927.json).
- 배포된 compare JS의 클라이언트 생성 경로는 연결 설정 오류를 직접 throw한다. usable한 URL/key가 빌드 결과에 반영되지 않은 증거다. 현재 변수 이름이 존재한다는 것만으로 빌드 당시 값의 유효성을 확정하지 않는다.
- [Next.js 15 공식 문서](https://nextjs.org/docs/15/app/guides/environment-variables)에 따라 `NEXT_PUBLIC_*`는 빌드 때 고정된다. Production의 두 공개 변수 값을 원격 Supabase 값으로 확인하고 빌드 캐시 없이 재배포한 뒤 JSON을 다시 검증해야 한다. 이번 요청은 확인 범위여서 Vercel 값이나 배포를 변경하지 않았다.
