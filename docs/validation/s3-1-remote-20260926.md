# S3-1 원격 실행 — 8GB 확장·복원과 제품 경로 검증 완료

사용자는 8GB 확장과 단계별 복원 재시도를 승인했다. 아래에는 첫 HTTP timeout까지의 이력을 보존한다. 후속 승인으로 직접 SQL 웜 p95 52.203~220.983ms 및 익명 로그인 세션 HTTP 186회를 통과했고, Auth·Vault·비활성 웹훅 준비도 완료했다. 최종 상태는 [제품 경로 재검증](s3-1-product-rpc-20260926.md)을 따른다.

## 디스크 원인·비용·확장 확인

이전 복원 232.403초 시점인 **10:59:34.730 UTC** Postgres 로그를 재조회했다. `could not write to file "pg_wal/xlogtemp.5666": No space left on device` 이후 WAL writer가 signal 6으로 중단되고 다른 활성 서버 프로세스가 종료됐다. [재확인 원문](s3-1-disk-cause-confirmed.json). 주 원인은 **디스크 부족**이며, TCP keepalive는 보조 연결 유지 조치다.

확장 전 API 조회: gp3 2GB, 3,000 IOPS, 125MiB/s. [공식 요금표](https://supabase.com/docs/guides/platform/manage-your-usage/disk-size)는 Pro 기본 DB의 gp3 8GB까지 디스크 추가 요금이 없다고 명시한다. 사용자가 확인한 Marketplace Pro 조건에서 용량만 8GB로 변경했으며 IOPS·처리량·컴퓨트는 변경하지 않았다. 조직 청구/entitlements API는 현재 토큰에 HTTP 403을 반환해 실제 청구서는 독립 조회하지 못했다. **8GB 디스크 증분 요금 0은 공식 Pro 포함 기준에 대한 확인**이며 청구서 열람 결과가 아니다.

- `POST /v1/projects/{ref}/config/disk` 요청: gp3 8GB / 3,000 IOPS / 125MiB/s. HTTP **201**, 접수 **3.314초**. [요청 기록](s3-1-disk-resize-request.json).
- 요청 접수만으로 완료 처리하지 않았다. 실제 파일시스템 확장과 SQL 정상 연결을 15초 간격으로 두 번 확인했다. 준비 확인 루프 **82.387초**, 최종 관측 **12:06:27 UTC**. [완료 기록](s3-1-disk-resize-ready.json).
- Postgres 시작 시각은 확장 전과 같은 `2026-09-26T08:54:10.488023+00:00`. 이번 확장은 재시작 없이 반영됐고 프로젝트 상태는 `ACTIVE_HEALTHY`였다. 별도 재시작은 실행하지 않았다.
- 관리형 DB 서버의 셸 접근이 없어 `df` 명령은 직접 실행하지 못했다. 대신 Supabase Metrics API의 실제 `/data` `node_filesystem_size_bytes`·`avail_bytes`·`free_bytes`로 확인했다.

## HTTP 검증 실패 원인과 범위

12:21:18 UTC의 Postgres·PostgREST 로그: SQLSTATE **57014**, `canceling statement due to statement timeout`. [로그](s3-1-http-timeout-logs.json). 같은 시점 읽기 전용 role 설정 조회에서 `anon`은 **3초**, `authenticated`는 **8초**였다. [role·DB 상태](s3-1-http-timeout-state.json). 디스크 부족 재발로 판단하지 않는다.

검증 함수는 18테이블 대조와 6조합 DB 측정·p95 기준 검사를 모두 통과한 뒤 HTTP 루프로 진입했다. 각 조합 30회씩 순차 호출하는 코드와 [HTTP 건수 로그](s3-1-http-counts.json)의 **200 150건 / 500 1건**을 대조하면, 앞의 5조합은 응답 대조를 통과했고 6번째 **한티 1,000m 첫 HTTP 호출**에서 중단된 것으로 추론된다. 요청 body는 로그로 직접 확인하지 않았다.

검증기는 전 과정 성공 시에만 결과 JSON을 저장한다. 이번 실패에서는 DB·성공 HTTP의 개별 시간 배열/p95 보고서가 생성되지 않았으므로 수치를 복원해서 기재하거나 6조합 완료로 표시하지 않는다. HTTP 3초 제한을 넘긴 세부 실행 계획 원인은 아직 조사하지 않았다. timeout 값을 임의로 늘리거나 실패 요청을 재시도하지 않았다.

## 남은 작업

HTTP RPC timeout 원인 조사·해결 및 6조합 DB/HTTP 재검증이 필요하다. 그 후 승인된 순서대로 Auth→Vault를 진행한다. 웹훅 활성화는 main 머지 이후, Vercel 연결·도메인·Auth URL은 사용자가 수행한다. `INGEST_REMOTE_ENABLED=false`를 유지하며 Ready 전환은 HTTP 검증과 후속 설정 완료 후로 남긴다.
