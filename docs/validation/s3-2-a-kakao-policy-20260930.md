# S3-2 A 착수 — 카카오 결과 저장 정책 확인

2026-09-30. 사용자 지시대로 코드 구현 전에 확인했다. **양수 TTL은 확정하지 않았다.** D2의 uid별 캐시와 결과 영속 저장 계획이 공급자 안내와 충돌하므로 해당 구현을 보류하고 사용자에게 보고했다.

## 확인한 1차 자료

- [Kakao Developers 서비스 약관](https://developers.kakao.com/terms/ko/site-terms), [운영정책](https://developers.kakao.com/terms/ko/site-policies): 검토한 본문에서 Local 응답을24시간 등으로 캐시할 수 있다는 별도 허용 TTL을 확인하지 못했다. 해당 문서에 제한이 없다는 결론으로 해석하지 않는다.
- [카카오 Map 담당자의 2025-07-22 답변](https://devtalk.kakao.com/t/api/145284): 장소 북마크의 DB 저장과1~24시간 성능 캐시를 묻는 질문에 Local 응답 데이터의 저장 이용을 금지하고 실시간 호출을 안내했다. 식별키에 대한 답변도 있으나 후속 답변과 범위가 달라 전체 식별자 정책으로 일반화하지 않는다.
- [2026-02-02 저장 범위 답변](https://devtalk.kakao.com/t/api/148194): 응답 데이터를 별도 POI DB로 구축하지 말도록 안내하고 장소ID 저장과 재호출을 언급했다. 이를 주소·좌표·장소명 캐시 허용으로 해석하지 않는다.
- [2026-09-04·09-07 공식 답변](https://devtalk.kakao.com/t/local-api/151505): DB 저장 없이 실시간 비교 후 폐기하는 경로를 허용하며 독립 공공 데이터 저장은 별도 범위로 구분한다. 장소ID/URL에 대한 세부 안내와 응답 본문 저장 허용은 구분한다.

## 구현 판단

1. 성공24시간·빈 결과10분은 승인 전 계획의 제안치였으며 약관 검증값이 아니다. 이를 코드·DB default로 넣지 않는다.
2. 사용자에게 실시간 검색→독립 공공 원천 매칭→응답 폐기, `app_private`에는 요청/쿼터 메타데이터만 저장하는 변경안을 제시했다. 응답 미저장은 단순 TTL 설정 외에 후보 좌표·주소·fixture·로그 저장 경로도 함께 바꾸는 결정이다.
3. 확정 전에는 카카오 응답 캐시·영속화·새 응답 기록을 구현하지 않는다. 백분위 RPC·순수 채점 어댑터 등 독립 작업은 계속할 수 있다.
4. 기존 S1/R2/DB 지오코딩 자료는 이 조사로 삭제하거나 재적재하지 않았다. 기존 자료의 보존·사용 정책은 별도 확인 대상으로 보고한다.

## 추가 구현 조건

주소 API가 정상0건일 때만 장소 검색으로 폴백하고 두 호출 종류의 실제 요청 수를 별도로 집계한다. uid당 일100회는 제품 한도이며 Kakao 계정 쿼터 확인값이 아니다. 응답 출처는 주소/장소를 구분한다.

Route Handler는 사용자 지정 `icn1`(서울)에 고정한다. 한국 사용자·한국 주소 검색 호출의 지역을 고정하려는 결정이며, 현재 원격 Supabase 도쿄 리전과 동일하다고 표현하지 않는다. [Vercel 공식 설정](https://vercel.com/docs/functions/configuring-functions/region)에 따른 `preferredRegion`과 배포 산출물/실제 리전 확인을 분리한다.

실행: 문서 조회만 수행. Kakao 신규 API 호출·원격 DB 쓰기·기존 데이터 삭제 없음.
