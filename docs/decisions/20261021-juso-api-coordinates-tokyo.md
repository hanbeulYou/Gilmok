# ADR — Juso API 좌표를 기존 도쿄 DB에 저장

- 결정일: 2026-10-21
- 상태: **사용자 결정 확정 / 원격 migration·데이터 승격은 별도 승인 대기**
- 결정자: 사용자(서비스 운영자)
- 범위: Juso 검색·좌표 API 결과를 기존 Supabase 도쿄 리전 DB에서 사용하는 G/#40 전환. 파일 배포 DB로의 교체는 채택하지 않는다.

## 배경

Kakao 좌표 응답의 저장 조건과 Vworld 지오코더의 저장장치/DB 저장 금지 안내 때문에 주소 공급자를 Juso로 전환했다. G(#39)는 Juso API 재산출·학교 공공 좌표 보완·원자적 승격/rollback을 로컬에서 검증했으나 국외 저장 조건 회신을 기다리며 원격 승격을 보류했다. 사용자는 2026-10-21 공식 문의를 무응답으로 종결하고 현재 도쿄 DB를 유지하기로 결정했다. 기존 Kakao/Vworld 저장 자료와 키의 삭제를 이번 결정에 포함하지 않는다.

직접 문의 접수일/게시글 번호와 공개 답변 부재는 [조회 증거](../validation/juso-inquiry-147547-20261021.json)로 확인했다. 별도 긍정 답변의 원문/날짜는 보완할 항목이다. 공식 허가나 묵시적 허가를 받았다고 기록하지 않는다. 이전 문서의 ‘제5조제3항은 제한제공 자료에만 해당’이라는 축약도 확정된 법적 적용 범위로 인용하지 않는다.

## 결정

1. 문의를 무응답으로 종결하고 Juso API 좌표를 **기존 도쿄(ap-northeast-1) Supabase DB에 저장**한다. 이는 위 확인 사실과 남은 불확실성을 전제로 한 운영자의 결정이다.
2. 위치정보요약DB 조사를 중단한다. [대안 기록](../planning/juso-file-source-alternative.md)만 남기고 신청·다운로드·파일 기반 공급자 구현을 진행하지 않는다.
3. #39는 최종 dry-run/쓰기 범위 보고 → 별도 승인 → 원자적 승격 → 원격 a~e 검증 순서다. #40은 그다음 migration push → 사용자 머지·Production 배포를 한 세트로 취급한다. 머지 전 Vercel의 서버 전용 `JUSO_API_KEY`, `JUSO_COORD_API_KEY` 존재 확인을 요청한다. #41 Ready는 앞 단계 보고/확인 후 진행한다.
4. 이번 결정은 G 승격의 승인 전제였던 ‘Juso 공식 회신 대기’를 해제한다. **migration push·원격 데이터 쓰기·리전 이전·기존 좌표/키 삭제를 지금 실행하라는 승인은 아니다.**

## 잔여 리스크

- 일반약관의 저장 금지 문구 부재와 API 카탈로그만으로 공개 좌표 API의 해외 영속 저장·백업·지도 표시까지 명시적으로 확인하지 못했다. 별도 긍정 답변의 날짜와 적용 대상도 미검증이다. 직접 문의147547에는 현재 공개 답변이 없다.
- 서비스의 처리 위치와 DB 위치는 다르다. Route Handler `icn1`은 도쿄 DB나 백업의 위치를 바꾸지 않는다. R2·CI artifact 등의 저장도 일괄 허용으로 간주하지 않는다.
- 문의 무응답은 허가가 아니다. 이후 제공기관 안내·약관/법령 변경 또는 적용 범위 확인에 따라 삭제/중단/서울 이전이 필요할 수 있다.
- **추정**: 현재 카탈로그·약관 상태를 근거로 저장 지속이 가능할 것이라는 운영상 판단은 있을 수 있으나, 공식 개별 확인 사실로 사용하지 않는다.

## 완화책과 삭제/이전 가능성

- 승격 직전 **원격의 실제 기존 상태**를 COPY BINARY + 테이블 행수·gzip/binary SHA256·source fingerprint로 로컬 rollback manifest에 보존한다. 로컬 실험 DB의 과거 백업을 원격의 이전 상태로 간주하지 않는다. G의 12테이블 실패/복원 검증은 [기존 검증](../validation/academy-coordinate-transition-20261013.md)을 따른다.
- 요청 시 신규 도입 좌표를 제거하고 이전 상태로 복구할 수 있도록 provider·revision·원본 hash·명시층·품질 보류·release를 함께 관리한다. 기존 Juso 행/이후 추가된 사용자 데이터까지 무조건 덮어쓰는 복원은 금지하고 삭제 요청 범위별 영향 목록과 승인을 먼저 받는다.
- **rollback은 모든 사본의 삭제와 다르다.** DB 복구 후에도 좌표가 든 로컬 binary/원본·R2·로그·관리형 백업이 남을 수 있다. 삭제 요청 시 사본 inventory를 포함하며 관리형 백업은 공급자 보존 정책/삭제 가능 범위를 확인한다. 현재는 삭제를 실행하지 않는다.
- [A0 §9의 서울 리전 이전 절차](../planning/s3-2-a0-juso-plan.md#9-조건부-supabase-서울-이전안--미승인)를 보유한다. 새 서울 프로젝트·비용 확인 → schema/Auth/uid/RLS 포함 복원 → digest/6조합/사용자 데이터 검증 → Vercel·Actions 연결 전환 → 구 프로젝트 보존 후 정리 순서이며 이전 자체는 별도 승인한다. **이전 계획이 있으며 실제 서울 이전을 검증 완료했다는 뜻은 아니다.**
- 이번 G 승격은 DB 변경 범위를 고정해 승인받는다. R2 새 좌표 게시, Kakao/Vworld cache/키 삭제, 법적 의미가 다른 파일DB 제공 조건 수락은 자동 실행하지 않는다.

## 재검토 조건

제공기관의 후속 답변/삭제 요청, API 약관·카탈로그·관련 규정 변경, 게시판 답변 원문 확보 후 현재 해석과 충돌, 새 국가/리전·백업/공개 재배포 범위 확대, 삭제 또는 rollback 불능 발견 시 재검토한다. 필요하면 신규 좌표 저장을 중단하고 원천/출처 표시를 정정하며, 삭제·서울 이전은 검토한 manifest와 사용자 승인으로 실행한다.
